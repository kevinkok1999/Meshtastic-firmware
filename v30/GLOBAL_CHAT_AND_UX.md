# V30 PRO — worldwide messaging, browser chat and complete UX
Date 2026-11-17. User-approved additional product requirements. Mandatory for FINAL/STABLE; not implemented or verified merely by this specification.

## Preserve every agreed capability
Do not remove V27 zero-config world messaging, V28 browser/chat and join flows, V29 emergency, RF, wallpaper, existing tools, legacy channels/contact/history, P1 V8 native compatibility or V30 MeshMap Nano. Retain advanced diagnostics behind separate menus; if a hardware capability is absent, explicitly show why, never pretend success. Future supplementary transports (ESP-NOW, BLE direct) have explicit device capability negotiation and real tests. No downgrade of privacy or regional radio constraints to obtain feature parity. No mandatory SD, phone, or internet for offline LoRa/map use.

## One native conversation, one identity
- Preserve RF-first scheduling intent: attempt/admit LoRa if permitted by shared governor; when airtime/capacity prohibits RF, record deferred and allow authenticated Internet without waiting for a physical send. Do not deliberately block global delivery waiting for a radio channel; no duty bypass. Internet never disables RF. If both capable/healthy, one logical ID (origin full key + per-message ID) and one conversation; no duplicate self-echo or UI bubble. Local journal is authoritative. Transport result is not recipient delivery.
- One verified end-to-end envelope shared across capable transport routes. Legacy native messages remain explicit compatibility lane; don't claim identical wire protocol or private security across mismatched protocols. Define bridge mapping and dedup tests, no automatic Internet-to-RF flooding or forwarding loops.
- Wi-Fi saved once, automatic reconnect, distinct AP/DHCP/DNS/WAN/TLS/relay states. Device can use Internet from two unrelated Wi-Fi/hotspot networks. Local Wi-Fi/ESP-NOW/BLE paths only where verified supported and authenticated. Optional gateway (Ethernet/5GHz upstream separate hardware, 2.4GHz device AP), never mandatory. P1 V8 BLE/native LoRa only until a separately proved role. Open Wi-Fi opportunistic mode remains opt-in untrusted network, TLS/E2E only, no local admin exposure or trust promotion. Existing privacy protections never prevent normal safe messaging.
- Delivery text: "Sending", "Queued", "Sent" (physical TX/relay accepted indicated separately in details), "Delivered" only recipient-verified acceptance; "Offline – mesh available". Explicit no-route state with retry and no false promise that user receives messages when off-grid.

## Browser chat and simple onboarding
- Device's local companion browser root opens directly into Chats. One native conversation store/actual existing WebSocket command path; no second message engine. Home/Chats, New Chat, Join Channel, contact search, private/public channel label, recent chats, composer, offline queue and connection status. Responsive keyboard/touch desktop/mobile and 320x240 native UI. Saved Wi-Fi auto-connect; when users open the provided local URL or browser chat shortcut they see Chats, not an engineering dashboard. Captive-portal auto-popup depends on OS, offer QR/local address fallback without promising automatic launching of a browser on any OS.
- Local browser requires authenticated pairing/physical confirmation and protected session; no privileged action merely by joining AP. Never embed a device private key or channel secret in browser URLs or logs. Authenticated local session via approved safe transport/origin and CSRF, no exposed general LAN admin. Web chat on another network requires authenticated end-to-end global client or device pairing; no plaintext server copy.
- Channel UI: Public: same normalized public hashtag in same network scope -> same public conversation, clearly public. Private: same exact existing high-entropy 128-bit channel key (32 hexadecimal characters) -> one opaque capability derived locally with standard domain-separated HMAC; same key automatically joins existing normal conversation, no extra broker settings. Different key -> different channel even if friendly display name identical. Keep existing V28 key compatibility; labels do not silently derive a weaker key. Device-local secret input masked, no URL, clipboard/export deliberate confirmation, QR optional.
- Preserve V28 8-character invite locator XXXX-XXXX, not a real key or direct key derivation. Server knows only invite hash + required authorization metadata; short TTL and signed/request rate-limits. High-entropy QR invite can support auto-approved single-use invitation; short code follows explicit owner-approved or securely configured invite policy. Real random channel secret delivered encrypted to approved device. Join success opens existing conversation immediately; pending/offline/denied/expired states provide next action. No automatic unsafe approval based only on guessable code. Removing member requires key epoch rotation.
- Global secure channel identity, labels and human display names are not proof of identity; exact keys/authentication matter. Keep channel secrets, private keys, Wi-Fi passwords, plaintext messages/contacts/GPS local.

## Production server contract (reuse V28 existing architecture, not new unrelated backend)
- Existing V28 HTTPS relay path and Vercel/Neon backend are candidate reuse; audit actual implementation and dependencies. Do not claim production operational until health, signed auth, quotas, replay, TTL, encrypted offline sync, receipt tests pass. HTTPS server hostname and certificate chain verified, no setInsecure/downgrade; fail closed global path while RF works.
- Device proves key possession; short lived scoped/grant/revocation, no service keys in firmware; opaque per-conversation capabilities, rate-limit and least privilege. Ciphertext-only bounded store+forward, TTL/deletion, replay/idempotency and receipt validation. Avoid wildcard access, log only redacted diagnostic counters. No anonymity claims (IP/timing metadata unavoidable).
- Under constrained RAM/flash (app budget ~180864 extra bytes as of V29), reuse existing V28 bridge/browser/native code; profile and compile after each change. Distinct browser assets can live outside app only in verified independent space, never overwrite map/identity/OTA. Map safety and RF latency always maintained.

## Verified inherited implementation and known gaps (read-only specialist audit)
V28 does have actual firmware V11GlobalBridge.cpp/.h (signed HTTPS, pinned CA, AES-GCM fixed 320-byte envelope, RF-first mirror, opaque route token and short join controls) and WebSocket companion patch in apply_v28.py. The embedded browser is local device companion, not verified globe-accessible Web application. Website source lib/v28-relay-db.js and lib/v28-relay-handler.js, /api/v28-relay rewritten via vercel.json, require configured DATABASE_URL and Neon dependencies. No new production network requests performed.
Known gaps: RAM pending arrays 16 DM/8 channel/8 ACK, six-hour expiry, head drops, 64-entry volatile dedup, not durable across reset. V28 HMAC(timestamp+text) IDs can collide across origins for same text/time; DB unique(route_token,message_id) can collapse messages. Use origin-bound logical IDs, durable journal and migration/compatibility contract; UTF-8-safe text limits (V28 MAX_TEXT 160 bytes truncates). Channel capability already HMAC(secret) ignoring friendly label; preserve legacy, distinguish optional future name-bound mode. Local upstream WebSocket /term handshake lacks equivalent paired session/Origin authentication; secure before exposing on shared Wi-Fi. Relay signed request quotas per self-generated device key alone insufficient: rate limit device/IP/opaque route/invite, short scopes, authorization, migration-controlled schema, TTL/offline/reboot tests. Actual live global messaging not demonstrated. No separate network dependency for normal LoRa.
